Overview

Intelligence Hub is Carsupermarket's internal website for buying, pricing and reporting on used cars. Buyers use it to value supplier stock lists and decide what to buy; managers use it for KPI dashboards, the Weekly Business Review and sales reports; the admin uses it to run data refreshes and manage users.

It is one Python web application (FastAPI with Jinja HTML templates) packed into a Docker image and run on AWS Lambda behind API Gateway. It keeps its own working data in an Aurora PostgreSQL database, reads reporting data from Snowflake (built by the dbt projects), stores files in S3, and calls outside services such as CAP HPI, Autotrader, DVSA, Microsoft Graph (SharePoint and email) and Google Slides.

Business And Industry Knowledge

Carsupermarket buys used cars in bulk from trade suppliers and sells them to the public online and from its sites. Most of the site exists to answer three questions: what should we buy, what should we pay, and how are we doing.

The Life Of A Car

  1. Supplier list. Suppliers (Enterprise, Motability, 1link, Purchase Pro, Universal and others) send lists of cars for sale, as a file, an email or on their own website.
  2. Valuation. Each car is valued by registration (VRM) and mileage: CAP Clean (what the trade pays) and the Autotrader retail valuation (what the public pays), plus Autotrader's retail rating and days to sell. This is the Supplier Stock Evaluator and Assess Vehicle.
  3. Buying decision. Buying Requirements shows, for each model (CAP ID) and price band, how many we sold in the last 90 days, how fast, at what margin, and how many more we should hold.
  4. Purchase. The buyer agrees the price. The purchase goes on the Daily Buyers Sheet and the Cars Bought sheet (SharePoint), and the invoice is read by Cars Bought.
  5. Stock. The car arrives, is prepared (prep / reconditioning costs), priced and advertised on Autotrader and the website. Stock lives in Apex (the dealer system) and AutoView (costs).
  6. Order. A customer pays a deposit: status ORDERED (STATUS_ACKNOWLEDGED).
  7. Delivery. The customer collects and the balance is paid: status SOLD (STATUS_PAID). A credited invoice means the sale was reversed and it is left out.
  8. Trade disposal. Cars not worth retailing are sold at auction or to the trade (Trade Report).

Pricing Benchmarks

  • CAP Clean is the trade benchmark used for purchase prices. CAP Retail exists but is rarely used. "Live" CAP values are adjusted for the exact mileage; "monthly" values come from the monthly CAP book.
  • Autotrader valuation is the retail benchmark for selling prices. Normal stock sells at about 98% of it.
  • 0% (interest-free) cars sell at about 125% of the Autotrader valuation, because the higher price pays for a subsidy (about 14%) charged by the finance company. They must be left out of any price-based average (sell price, AT valuation, price to market) but kept in counts and non-price figures. In code the band is interest_free; Snowflake sends 0%, which is renamed on arrival; the page shows "0%".

Running It Locally

Run python main.py from source_code/router/backend; the site opens at http://127.0.0.1:8080/. It uses uvicorn with auto-reload.

  1. Install Python 3.12 and Poetry, then run poetry install --with dev in source_code/router.
  2. Sign in to AWS SSO (aws sso login, or the "Sign In To AWS" item in the account menu, which only appears when running locally). The app reads all logins from Secrets Manager, so nothing works without a session.
  3. Set LOCAL_ENV=1. This makes the session cookie work over plain http and runs background jobs in a thread instead of calling Lambda.
  4. Leave AWS_REGION unset or set it to us-east-2. Anything with AWS_REGION=eu-west-1 is treated as production, including your laptop.
Careful: a local run still writes to some production tables (KPI layout, page names, WBR comments, budgets, SharePoint sources, AI knowledge) through get_prod_pricer_connection, and always reads production Snowflake. Settings > Live Update starts production dbt jobs from any environment.

Other ways to run it: the VS Code launch config (port 8000), or docker-compose.yml (Lambda emulator on port 9000, plus local Postgres and Redis). The compose file sets AWS_REGION=eu-west-1, which makes the container act as production; change it before using it. README.md is out of date (Python 3.9, conda).

What Terraform Builds

  • Lambda (modules/lambda/docker/vpc/lambda.tf): image-based, 3072 MB, 600 s timeout, in two private subnets of the default VPC with its own security group. Logs go to /aws/lambda/<function> for 60 days. ignore_changes = [image_uri]: Terraform never changes the code after creation; CI does.
  • API Gateway (modules/api_gateway/api.tf): REST API, regional, {proxy+} and / both pass everything to the Lambda, no authorizer (the app does its own login). Requests are cut off at 29 seconds by API Gateway, whatever the Lambda timeout.
  • Domain: ACM certificate, a Route53 zone per site name delegated from aramis-group.eu, a regional custom domain and base path mapping.
  • Security group (modules/vpc/security_group/sg.tf) plus a rule letting it reach Aurora on port 5432.
  • IAM role (modules/iam/): S3, CloudWatch Logs, invoke Lambda (used for background jobs), Textract AnalyzeExpense, Secrets Manager read, ECS run/stop task (dbt runs) and pass-role for the dbt task roles.

Not in Terraform: the S3 bucket, the secrets, Aurora itself, ECR repositories (made by CI), any alarms or schedules. Terraform state is in S3 bucket aa-terraform-running-tfstate-prod, one key, with dev and prod as workspaces. terraform/dev and terraform/prod hold the same files.

Docker Image

source_code/router/Dockerfile has two stages on public.ecr.aws/lambda/python:3.12. The first exports Poetry dependencies and installs them into /python_build. The second copies them in, installs Chromium's system libraries, runs python3 -m playwright install chromium (Playwright is not on the PATH), copies backend/ and starts main.handler. The running image uses TZ=Europe/London.

Deployment

Merging to main deploys production; merging to dev deploys dev. .gitlab-ci.yml uses shared templates from the data platform GitLab project.

  1. .pre: work out region and environment from the branch, make sure the ECR repository exists.
  2. build_docker_image: build and push the image to ECR. plan_tf runs alongside.
  3. deploy_docker_image: point the Lambda at the new image. This is what puts code live.
  • Terraform changes to prod are applied by hand by the platform team. Never apply an old plan_tf plan: on 2026-10-19 that rolled the site back to old code.
  • There is no test or lint stage. Run the tests yourself before merging (see Tests).
  • A pre-commit hook blocks commits straight to main and dev.
  • Browser files are cache-busted: static_url() adds ?v=<hash of the file>, and those URLs are cached for a year, so a deploy always serves the new JS and CSS.

Backend Application

main.py builds the FastAPI app; routers/__init__.py combines every router; routers/core.py holds what they all share.

Request Path

  1. API Gateway passes the request to Mangum (handler in main.py).
  2. Middleware, outermost first: GZip (keeps big JSON under Lambda's 6 MB response limit), the base path middleware (redirects old /dev/... links, times the request, records slow ones), then the session middleware (signed cookie).
  3. The route runs. Page routes use Depends(require_page('key')); data routes use Depends(require_page_api('key')); admin routes check is_admin(user).
  4. Errors: PageRedirect becomes a 303 redirect; other errors render error.html (a database connection error shows "Database Unreachable").

Caches Inside The App

  • Users, page access, page names, appearance and session settings are read from Aurora and kept in memory for 30-60 seconds per Lambda container.
  • utils/cache.py @cache keeps Autotrader answers in memory for 24 hours.
  • Snowflake results are cached in memory and in S3; see Snowflake.
  • Several Lambda containers can run at once and each has its own memory, so an in-memory change (for example new CAP credentials) only reaches the other containers when their cache runs out or they restart.

Logging

utils/app_log.py writes to the Aurora app_logs table: every warning and error, every Snowflake query, SharePoint activity and requests slower than the logs_slow_request_ms setting (default 1000 ms). Rows are kept for logs_retention_days (default 30). The admin reads them on the Logs page. Everything also goes to CloudWatch.

Authentication And Access

The site has its own username and password login, kept in Aurora, with a signed session cookie. API Gateway does no checking.

Login

  • Sign-in is Keycloak single sign-on (routers/auth.py, utils/keycloak_auth.py). The callback matches the email Keycloak sends to exactly one row of the users table (case does not matter), then starts the session under that row's username. There are no passwords in this app.
  • The session cookie (Starlette SessionMiddleware) is signed, not encrypted, and lasts 30 days. It holds the username, the password hash, a session ID and the login time.
  • Each login is a row in user_sessions. The idle timeout (session_timeout_minutes) closes the activity row and starts a new one; it does not sign the user out. Sign-out happens on logout, Force Re-login, a password change, user deletion or cookie expiry.
  • Password rules (utils/password_rules.py): at least 6 characters, a digit, an upper-case letter and a symbol.

New Users And Password Links

  1. The admin adds a user on Settings > User Accounts. A new user is inactive, has an unusable password and no pages.
  2. The admin creates a set-password link (valid for password_link_hours, default 48) and emails it through Microsoft Graph.
  3. GET /set-password only checks the link, so email preview tools do not use it up. POST /set-password sets the password, activates the user and ends their other sessions.

Only a hash of the link token is stored (password_links). Making a new link cancels older unused ones.

Page Access

  • routers/page_registry.py is the one list of pages that can be granted. Each has a key, a path, a label and whether it is a default.
  • Grants are in user_page_access. A user never configured gets the defaults (Buying Requirements, Supplier Stock Evaluator, Orders & Deliveries). Once saved, a user gets exactly what was ticked, kept apart from "never configured" by a __configured__ marker row.
  • Settings, Logs, Users and this Technical Guide are not in the list: they are admin only and cannot be granted.
  • To add a page: add a Page to PAGES, put require_page on its route and require_page_api on its endpoints. The home tile and the Page Access column follow automatically.
  • Roles and permissions (user_roles): one role, buyer, and one permission, approve_site_changes.

Shared Vehicle Store

Assessing, pricing and buying share one set of tables keyed on VRM and supplier, through utils/vehicle_store.py and utils/supplier_store.py. Never add a separate copy of vehicle, supplier, CAP, Autotrader, RRP or prep cost data for one page.

  • vehicles: one row per VRM, with Autotrader and CAP identity and spec.
  • vehicle_valuations: one row per lookup (VRM + mileage rounded to 1,000). Reused for valuation_cache_hours (default 36), so the same car is not paid for twice.
  • supplier_vehicle_listings: every car on every imported list (price history).
  • supplier_vehicle_status: one row per VRM and supplier: first and last seen, removed, current and previous price.

How The Schema Is Made

Most tables are created by the app the first time they are needed (CREATE TABLE IF NOT EXISTS, run once per container through utils/ddl_once.py). The db/ SQL files are a record of the main tables, not a full or re-runnable set. To add a column, follow the module's existing _ensure_... function and add a matching db/ file.

Snowflake

Snowflake holds the business data (stock, sales, finance, marketing), built by the dbt projects. Intelligence Hub only reads it, always from PROD_CARSUPERMARKET_DB.

  • utils/snowflake_client.py logs in with username and password from prod/carsupermarket/core/snowflake/data_analyst_credentials, the same in every environment. It keeps up to 4 open connections per container and retries once on a dropped connection. Every query is written to app_logs.
  • Names: SOURCE_* schemas are raw data (dbt __s models), COMPUTE_* are business logic (__c), PRODUCT_* are finished tables for reports (__p).
  • Only PROD dbt is scheduled (Rundeck, at about 08:15, 10:15, 12:15, 14:15 and 16:15 UK). Several caches here expect those times.

Caching Snowflake Results

  • Most pages keep results in memory, then in S3, and only query Snowflake when both are out of date.
  • S3 cache files have a version in the name (for example buying_requirements_v25.json, orders_deliveries_v14.json). When a query adds or removes columns, raise the version number, or the old file is served and new columns show blank.
  • Buying Requirements and Orders & Deliveries treat their cache as fresh until 45 minutes after the next dbt run time.
  • Files under .../shared/ are used by dev and prod alike.

Snowflake Cortex (Snowflake's built-in AI) must not be used. utils/cortex.py now always raises AIUnavailable, so Ask AI on KPI and Orders & Deliveries is switched off until it is rebuilt on another AI service.

Every outside service, what it is for, and how it is called. CAP and Autotrader calls are throttled by utils/rate_limiter.py; their limits are on Settings > Page Settings > Supplier Stock Evaluator (cap_workers 25, cap_rate_limit 100/s, at_workers 40, at_rate_limit 60/s).

CAP HPI

Trade valuations. clients/cap_client.py, SOAP-style form posts to soap.cap.co.uk: valuation by VRM, live value by CAP ID and registration date, monthly value, model image. Login from api_access, or the override on Settings > CAP Credentials. 20 s timeout, 3 tries. Used by the Supplier Stock Evaluator, Assess Vehicle, CAP Lookup and Cars Bought.

Autotrader Connect

Retail valuation, retail rating, days to sell, vehicle data and features, keeper history, advert allowance. clients/autotrader_client.py, api.autotrader.co.uk (/authenticate, /vehicles, /valuations, /advertisers). Answers are kept in memory for 24 hours. A supplier run stops after 10 "too many requests" replies. For advert status use only adverts_retail_autotrader_advert_status.

HPI Spec Check

The options a car left the factory with. clients/spec_check_client.py, SOAP to wss.hpi.co.uk (live only; our login does not work on the test service). Every call is billed, so it is a manual button on Assess Vehicle only, behind a confirmation, and every answer (including "no data", codes 103 and 120) is stored for ever in vehicle_spec_checks and never asked for again.

DVSA MOT History

Government MOT test history. utils/dvsa_client.py: Microsoft login token, then history.mot.api.gov.uk/v1/trade/vehicles/registration/{vrm} with an API key. Used by MOT Check, which flags mileage going backwards and early tests.

Microsoft Graph (SharePoint And Email)

  • SharePoint (utils/sharepoint_client.py, utils/sharepoint_sources.py): reads workbooks from carsmkt.sharepoint.com, for example the Daily Buyers Sheet, Cars Bought, Daily Spend and Enquiries, Autotrader CTR and the WBR sheets. The list of files is on Settings > SharePoint. Before using a copy, the app asks Graph when the file was last saved; a newer file is downloaded by a background job and kept in memory and S3. Workbooks are read with python-calamine.
  • Email (utils/email_client.py): sends as intel-hub@carsupermarket.com through the Website Mailer app. Used for password links, Developments emails and the test email.
  • Cars Bought invoice folder: PDFs dropped in Department/Buying/Invoices are picked up and read.

Nexus Point (Apex Data API)

Apex's data, from data-api.nexuspointapex.com with a bearer token. utils/nexus_ingest.py (Settings > Live Update API pulls, which write the raw S3 files dbt reads, and the "Import From Nexus" user import) and reports/nexus_source.py (recent changes on top of Snowflake for Apex Reports). The API's updated_at filter is UK local time.

Google Slides

Exports the Weekly Business Review to a Google Slides deck. clients/google_slides_client.py and utils/google_oauth.py. The admin connects a Google account on Settings > Google (scope drive.file); the refresh token is stored encrypted in settings. Chart images are passed to Google as 10-minute S3 links.

Supplier Websites

Background Jobs

Anything that takes longer than a page can wait for runs as a second call to the same Lambda, started in the background.

  1. The page posts to a start route. It saves a job row (Aurora table or S3 file) and returns straight away.
  2. The start route calls LambdaRequestsManager().simulate_http(...) (utils/lambda_http.py), which invokes the same Lambda with InvocationType='Event' and a made-up API Gateway request for the worker route. Locally (LOCAL_ENV=1) it runs in a thread instead.
  3. The worker route checks the worker secret, does the work (up to the 600 s Lambda limit) and writes progress to the job row.
  4. The page polls a status route and shows progress.

Supplier Stock Evaluator In Detail

  1. Upload (or Get Stock, or the Enterprise email) saves a tasks row and the file in S3 raw/.
  2. /elaborate-task downloads it and calls supplier_stock/batch_processor.process_file_with_cache.
  3. Rows are mapped to standard columns per supplier (clients/columns_mapper.py).
  4. Stored valuations still in date are read in one batch; only the rest go to CAP and Autotrader, both at once in their own worker pools.
  5. Results are written to the vehicle store in batches, price reductions against the last list are counted, and the output xlsx goes to S3 elaborated/.
  6. Progress lines are written to tasks.progress_message every 1.5 s; the page polls /api/tasks-json.

Buying Requirements Rules

  • A row is a CAP ID and price band. Bands come from Snowflake; cars on today's buyers sheet are banded from their RRP, and any car with an "RRP 0%" value goes in the interest-free band.
  • Days in stock, days to sell and margin averages use sold or ordered cars only (sales90 === 1). Max DIS, Max DTS and Min GPU-M filters apply to the table, the vehicle popup and the export.
  • Ideal Stock and Required are kept as decimals and shown to 1 decimal place; never round them before summing.
  • The export groups by CAP ID only and leaves interest-free cars out of price averages.

Orders & Deliveries Rules

  • Orders count STATUS_ACKNOWLEDGED and STATUS_PAID by order date; deliveries count STATUS_PAID by invoice date. Credited invoices are left out.
  • Covers the last three full months plus this month. Price, mileage and age bands are editable in its settings.

Front End

Every page is a full HTML file (no shared base template) that calls page_header(title, user) from _navigation.html and talks to the server with fetch() and JSON.

  • _navigation.html: the header row, side menu (built from user_menu() and the page categories in Settings > Page Names), alerts bell, live users and account menu.
  • static/css/theme.css: colours, borders, radii and the red-amber-green shading scale. Settings > Appearance overrides them. Check it before adding a colour to a page.
  • static/js/shading.js: shadeScale() for red-amber-green table cells.
  • static/js/charts.js: shared Chart.js helpers (target background, labels, day window).
  • Other shared JS: searchable_select.js (search box on long drop-downs), column_editor.js, colour_picker.js, popup_scroll_lock.js, date_range_jump.js, live_users.js, alerts.js, client_errors.js, account_nav.js.
  • Pages pass BASE_URL to JS as window.BASE_URL or a data-base attribute.

Rules For New Front-End Work

  • Make things editable on the page (a setting, a list to add to and rename) rather than fixed in code. Put sizes, colours and labels next to similar existing settings.
  • All visible text in Proper Case. No text-transform: uppercase except on number plates.
  • A popup that saves must grey out (busy on .modal-box), disable its button and show "Saving..." until done. Copy whileSaving() in trade_report.js.
  • Any new From / To date pair goes in PAIRS in date_range_jump.js.
  • Escape any server or user text before putting it in innerHTML.
  • Run node --check on every changed JS file: one syntax error stops the whole file and the page sticks on "Loading...".
  • Downloads of xlsx files must set the xlsx media type and an explicit Content-Disposition header.

Tests

Run poetry run pytest tests/ from source_code/router/backend. CI does not run them.

  • 26 files, mostly KPI, WBR, Cars Bought, User Guide, page access and password links.
  • Importing routers tries to load users from Aurora; without an AWS session it falls back quietly.
  • No tests yet for login, sessions, the supplier evaluator or background jobs.
  • Before merging: run the tests, node --check every changed JS file, and open every page the change touches.

Known Problems

The full list, with file references, how to fix and how to test, is in docs/improvement_plan.md. The most urgent:

  • Five background job routes run with no login or secret check, on a public address.
  • The session cookie signing key and the DVSA API login are written in the code.
  • Passwords are stored as unsalted SHA-256, and the hash is inside the readable session cookie. No limit on login attempts.
  • Supplier Stock Evaluator puts file names into the page without escaping them.
  • The Lambda role can read every secret and every S3 bucket in the account; the app uses the Aurora admin login.
  • Failed Autotrader calls are cached as answers for 24 hours.
